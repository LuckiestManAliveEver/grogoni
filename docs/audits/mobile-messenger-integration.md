# Messenger-first and unified conversation implementation review

Review date: October 23, 2026 (America/New_York). Scope: both supplied specifications, current working tree, and https://grogoni.com. This is an audit, not a remediation or deployment. Existing uncommitted changes were preserved.

## Result

The complete acceptance gate is not met. Production API workflows largely work, but actual push receipt remains unverified; the browser acceptance probe has a readiness problem; the local candidate contains authorization, notification, and contact regressions. Passing TypeScript does not establish acceptance.

Production acceptance run: **25 passed, 2 failed**. All three disposable accounts and the disposable business were removed and removal verified. Desktop and phone authentication discovery/start probes: **4 passed**, with disposable transaction cleanup. A subsequent diagnostic reported a browser pass, but inspection invalidates that conclusion: it counted a pinned shortcut while saved conversations were absent. See G13 and the strict follow-up evidence.

Local focused tests: **116 passed, 3 failed across 16 suites** (90 tests in the first run; 29 in the second). Mobile Chromium: **2 passed, 1 failed** ([failure screenshot](../testing/messenger-review-2026-10-23/local-mobile-auth-failure.png)). An additional isolated notification revocation reproduction failed, independently confirming a privacy regression. API and web TypeScript checks both passed. No complete repository test-suite pass is claimed.

## Verified production behavior

The fresh live API run exercised real sessions and disposable data, not mocked API responses:

- Permanent DAEMON identity is stable and discoverable; DIRECT has no fake agent/inference binding.
- Concurrent A→B/B→A creation returns one direct pair; encrypted sends/replays persist one message; both accounts decrypt and reply; plaintext direct submissions are rejected.
- Foreign accounts cannot read/write the tested direct, daemon, or business conversations. Foreign daemon-task association is rejected. Phonebook node selection reopens the pair and rejects another owner's node.
- Customer messages reach the business inbox; owner replies return to the same customer thread. Cross-tenant agent requests are rejected. Removed staff lose inbox, read, and write access.
- Authorized business inference produces a real response in the shared business conversation.
- Daemon execution returns a real `gpt-6-luna` response; the server projects it into the originating conversation without browser projection. Failure is visible, retry is owned, and encrypted direct messaging continues during the isolated task failure.
- Switching to the alternate configured model produces a second real response without replacing daemon history. This verifies model execution/selection, not semantic multi-turn recall or global provider outage behavior.
- API session/login and inbox restoration preserve all three conversation identities.

The production authentication smoke reaches the real `/auth/signup/start` and `/auth/login/methods` from desktop and 390px phone views and checks JSON 200 responses. It does **not** complete the public signup form, PIN setup, passkey ceremony, or installed-PWA session restoration. Fixture API PIN signup/login in the acceptance run is a separate, narrower test.

## Runtime/deployment limits

Real production responses verify the configured model IDs, including `gpt-6-luna` and the alternate model recorded in report.json. They do not independently identify every upstream provider hop or prove that historical OpenCode documentation describes current deployment. Do not substitute a provider based on old documentation. Server-side registry/provider routing and credential configuration should be attested from deployment/runtime trace metadata without exposing secrets. No credentials were printed or changed.

Required configuration includes connected frontend/API origins and cookies, durable conversation/daemon storage and deployed migrations, working daemon execution capacity, configured model registry/provider credentials on the server, and VAPID/service-worker/browser push support. No deployment, environment setting, account permission, or production schema was changed. Production writes were confined to disposable test accounts/businesses and their cleanup.

## Browser probe caveats

The first stricter follow-up used a fresh account whose only main conversation was the permanent daemon. After a 45-second wait, desktop and phone received authenticated bootstrap, conversation-list and thread HTTP 200 responses, with no page errors. The UI showed its pinned agent plus Help; ordinary `.conversation-item:not(.pinned-agent)` rows and type badges were absent. **That absence alone is not a defect:** the permanent daemon uses the pinned representation, and the phone inbox drawer was not opened. This check establishes successful authenticated API loading, not all-three-type UI restoration. Its screenshots and raw results are retained as `fresh-daemon-*`. The earlier diagnostic's one-row pass still does not prove saved direct/business restoration.

The final direct-conversation browser follow-up stopped at `/v1/session/context` HTTP 503 before launching the browser. Both disposable accounts were cleaned up and deletion verified. [Setup result](../testing/messenger-review-2026-10-23/strict-direct-setup-report.json) and [probe source](../testing/messenger-review-2026-10-23/strict-browser-probe-source.txt) are retained. There is no successful strict all-three-type browser restoration assertion from this review.
