## 1. Performance (blocks "instant")

- [ ] **Decide on snapshot query planning.** The `load` stage (165-190 ms warm) is mostly PostgreSQL planning a 154-arm `UNION ALL` on every request. The fix (parameterized SQL plus prepared statements through Neon's pooler, so plans are cached) is a production-risk change. Needs a decision first. Done when: `load` under 50 ms in `Server-Timing`, the full PostgreSQL lane is green, and there are no `prepared statement` errors in Edge logs for 24 h.
- [ ] **Measure acknowledgement from a Kenyan network.** All live numbers so far come from one machine with unstable connectivity. Run `scripts/measure-instant-messaging.mjs --live` from Safaricom and Airtel mobile data. Done when: before/after rows from a Kenyan network are in the audit doc.
- [ ] **Decide the Edge region if Kenya acknowledgement stays above 1 s.** Functions are pinned to `us-east-1` next to Neon `us-east-2`. Options: a closer region for both, or accept the network floor. Done when: decision recorded with measurements.
- [ ] **Measure inbound visibility.** Write a two-account harness: account A sends, and we time until B's open thread shows the message (SSE hint → delta read). Done when: the p50 and p90 are in the audit doc against the < 1 s target.
- [x] **Load-test the hint stream.** Every open SSE stream re-checks the session and queries the journal every 500 ms, about 2 transactions per second per connected user. Done when: database CPU and Edge cost are measured at 100 and 1,000 concurrent streams, and the interval or design is adjusted if needed. **Done (2026-11-21):** `scripts/load-test-hint-stream.ts` runs the production stream code against local PostgreSQL (4 cores) with 20 journal writes per second. Raw results: `/tmp/hint-stream-load/*.json`.

  | Design            | Streams | Transactions/s (designed) | Delivery p50 / p95 | PostgreSQL CPU, median | Pool waits |
  | ----------------- | ------- | ------------------------- | ------------------ | ---------------------- | ---------- |
  | Separate (before) | 100     | 330 (400)                 | 362 / 666 ms       | 62% of one core        | 4,059      |
  | Separate (before) | 1,000   | 733 (4,000)               | 2,613 / 4,193 ms   | 132%                   | 27,546     |
  | Combined (now)    | 100     | 172 (200)                 | 365 / 681 ms       | 85%                    | 1,219      |
  | Combined (now)    | 1,000   | 468 (2,000)               | 2,701 / 3,885 ms   | 167%                   | 18,260     |

  Design adjusted: the session check and the journal read are now one query in one transaction (`sessionJournalProbe` in `supabase/functions/api/application-routes.ts`), which halves transactions, round trips and pool waits per stream. Tests: `tests/message-event-stream.test.ts`, `tests/hint-stream-probe-postgres.test.ts`. At 1,000 streams the single local client process saturates first, so those delivery numbers are a floor for this machine, not an Edge figure.

  Finding: PostgreSQL CPU per probe did not drop, because it is dominated by planning each query (warm: 1.50 ms planning against 0.25 ms execution for the combined query; 1.50 ms against 0.26 ms for the old pair). That is the same root cause as **Decide on snapshot query planning** above: cached plans would cut probe CPU by about 6x. Without it, the other lever is checking the session every 5 s instead of every 500 ms (journal reads stay at 500 ms; a revoked session would keep receiving identifier-only hints for up to 5 s). Both are Julien's call. Edge cost: each always-connected user reconnects every 25 s, which is 3,456 invocations per day, or about 104 million per month for 1,000 such users.

- [x] **Decide the idle fallback cadence.** The remaining 9 requests per minute are the stream reconnect, the deliberate 30 s fallback checks (sync, inbox, open conversation), the notifications poll and a health check. Done when: the cadence is decided, for example a longer fallback while push is healthy. **Done (2026-11-21):** Kept at 30 s while push is healthy. While the stream reports healthy, the fallback is the only guard against a stream that stays open but stalls (for example a buffering proxy), and it costs about 2 small requests per minute. Revisit once the stream carries a heartbeat the client checks.
- [ ] **Watch isolate retirement.** Isolates now serve about 7 requests before `EarlyDrop`. Done when: a saved logs query (`SELECT log_attributes['reason'], count() … event_message = 'shutdown'`) is reviewed after a day of real traffic and the median requests per isolate is recorded.
